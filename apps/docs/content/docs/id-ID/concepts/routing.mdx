## Urutan keputusan

Untuk setiap request, router:

1. **Menerjemahkan `model`** mengikuti urutan di [Model & routing](/id-ID/docs/gateway/model-addressing): `chain:<nama>` → alias → `provider/model` → nama polos. Hasilnya daftar target berurutan.
2. **Memeriksa akses** — allowlist key ∩ plan, dan budget aktif.
3. **Memilih akun** — mengikuti [strategi akun](#strategi-akun) provider, melewati akun yang sedang cooldown atau dinonaktifkan. Akun lain tetap jadi fallback.
4. **Meneruskan request** — dan naik ke target berikutnya kalau gagal.

## Strategi akun

Tiap provider menentukan cara akunnya berbagi request (**Providers → pilih provider → Routing → Account strategy**, atau `PUT /v1/providers/:slug/routing`):

| Strategi          | `strategy`          | Perilaku                                                                                                                                                                    |
| ----------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Router default    | `default`           | Mengikuti **Settings → Routing**: round robin dengan sticky limit global saat provider round robin aktif, fill first saat nonaktif.                                         |
| Fill first        | `fill-first`        | Akun sehat dengan prioritas tertinggi menerima semua request sampai tidak tersedia.                                                                                         |
| Round robin       | `round-robin`       | Tiap akun menerima `sticky_limit` request, lalu akun berikutnya mengambil alih.                                                                                             |
| Smart round robin | `smart-round-robin` | Percakapan baru diputar (setiap `sticky_limit` percakapan); giliran berikutnya dalam satu percakapan tetap di akun awalnya, sampai percakapan diam selama `affinity_hours`. |

Smart round robin mengenali percakapan dari session id yang dikirim klien (`metadata.user_id` dari Claude Code, `prompt_cache_key` dari Codex), atau dari pembukaannya: system prompt plus pesan user pertama, per API key. Menjaga satu percakapan di satu akun membuat prompt cache provider tetap hangat. State rotasi disimpan di memori, jadi restart memulai tiap provider dari akun pertamanya lagi.

## Fallback chain

Chain menentukan siapa dicoba berikutnya. Contoh `heavy-coding`: Claude dulu, GLM kedua, OpenRouter sebagai fallback penutup. Kalau langkah pertama kena `429`, router masuk cooldown 30 detik untuk akun itu dan langsung lanjut ke langkah kedua — klien tidak melihat error.

Setiap langkah bisa dimatikan satu per satu (**Chains → edit → saklar langkah**, atau `"active": false` di API). Langkah yang nonaktif dilewati tapi tetap di posisinya, jadi menyalakannya lagi mengembalikan urutan semula.

## Retry dan cooldown

| Peristiwa                          | Tindakan router                                         |
| ---------------------------------- | ------------------------------------------------------- |
| Gangguan sementara (5xx, jaringan) | Retry di akun yang sama, maksimal 2x (jeda 500 ms, 1 s) |
| `429` dari upstream                | Cooldown akun 30 detik, hormati `Retry-After`           |
| Autentikasi upstream gagal         | Cooldown akun 5 menit                                   |
| Semua target habis                 | `503` ke klien                                          |

Total maksimal **10 percobaan** per request. Cooldown membuat akun yang bermasalah diistirahatkan, bukan dibanjiri lagi — statusnya terlihat di halaman **Provider Health**.

## Di luar chat

Request web search/fetch, audio, gambar, dan embeddings melewati pipeline yang sama: allowlist key dan plan, budget, prioritas akun, cooldown, dan fallback ke target atau akun berikutnya. Token embeddings dicatat dan dihitung biayanya seperti token chat.

## Konkurensi

Gateway membatasi request in-flight secara global (100). Saat penuh, request baru dijawab `503` — lebih jujur daripada antrean yang membengkak. Batas `rpm`/`tpm`/`concurrent` di plan tersimpan di skema, tapi belum ditegakkan gateway saat ini.

## Metering

Setiap request tercatat: provider dan model yang benar-benar melayani, key, akun, jenis klien (terdeteksi dari User-Agent — Claude Code, Cursor, Codex, Cline, Copilot, Aider, dll), token per kategori, biaya, cache hit, latensi, dan TTFT. Semua itu yang kamu lihat di halaman **Usage**.

<Callout type="idea" title="Latensi pertama token">
  TTFT (time-to-first-token) terukur per request — bandingkan provider lewat halaman **Usage**
  sebelum memutuskan urutan chain.
</Callout>
