title: Dashboard REST API
description: Reference for the REST endpoints that manage keys, providers, chains, guardrails, and usage.
---

All endpoints below live on the same server as the gateway (default `http://localhost:8080`) and power the dashboard UI. Great for automation and integrations.

For the inference endpoints, see the [Gateway API](/docs/gateway) section.

## Authentication

```bash
# sign in
curl -X POST http://localhost:8080/v1/auth/sign-in \
  -H "Content-Type: application/json" \
  -d '{ "email": "admin@tera.local", "password": "..." }'
```

```json
{
  "data": {
    "uid": "…",
    "email": "admin@tera.local",
    "access_token": "…",
    "refresh_token": "…",
    "expires_in": 3600
  }
}
```

- Access tokens last 1 hour; refresh tokens 30 days and are rotated on every renewal.
- Send the token in the `Authorization: Bearer <access_token>` header.
- `POST /v1/auth/sign-out` revokes all session tokens.

## Response envelope

| Shape            | JSON shape                                                |
| ---------------- | --------------------------------------------------------- |
| Single resource  | `{"data": …, "metadata": …, "message": …}`                |
| List             | `{"data": […], "metadata": {"total", "offset", "limit"}}` |
| Delete           | `{"message": "…"}`                                        |
| Error            | `{"message": "…"}`                                        |
| Validation error | `{"message": "…", "errors": {…}}` (422)                   |

Pagination uses the `offset` (0-based) and `limit` (default 10, max 100) query parameters.

### Playground

| Method | Path                    | Notes                                                                                                                                        |
| ------ | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/v1/playground/models` | Every model the playground can address: active catalog models of providers with a usable account (`provider/model`), then aliases and chains |

The model test endpoints take `{"model", "messages", "stream"}`. A streamed test is capped at 2 minutes.

### Proxy pools

| Method         | Path                           | Notes                                                           |
| -------------- | ------------------------------ | --------------------------------------------------------------- |
| GET / POST     | `/v1/proxy-pools`              | List / create pools                                             |
| POST           | `/v1/proxy-pools/bulk`         | Batch import `{"pools": [...]}`, all or nothing (max 500)       |
| POST           | `/v1/proxy-pools/bulk-delete`  | Delete `{"ids": [...]}`, skipping ones already gone             |
| POST           | `/v1/proxy-pools/relay-script` | Generate a relay script (`{"kind": "cloudflare"}` or `"local"`) |
| POST           | `/v1/proxy-pools/health-check` | Check all pools                                                 |
| PATCH / DELETE | `/v1/proxy-pools/:id`          | Edit / delete pool                                              |
| POST           | `/v1/proxy-pools/:id/test`     | Test one pool                                                   |

A pool URL is normally an HTTP/HTTPS/SOCKS forward proxy. A URL of the form `relay+https://:<secret>@host` is a fetch relay instead: the gateway sends each upstream call to the relay with the real target in `X-Tera-Relay-Target` and the secret in `X-Tera-Relay-Secret`. The relay-script endpoint returns a ready-to-deploy Cloudflare Worker or Node script with a fresh secret, plus the pool URL to register (replace `RELAY_HOST`).

### Restricted access

| Method    | Path                    | Notes                                         |
| --------- | ----------------------- | --------------------------------------------- |
| GET / PUT | `/v1/restricted-access` | Current allowlist period / replace it (whole) |

Body: `enabled`, `start_date` / `end_date` (`YYYY-MM-DD`, inclusive), `start_time` / `end_time` (`HH:MM`, repeats daily, may wrap past midnight), `timezone` (IANA, empty means UTC) and `allowed_ips` (addresses or CIDR ranges). Empty dates or times leave that side open. While the period is running, every path except `/health` answers `403 forbidden` to addresses off the list; loopback always passes. Enabling it without your own address on the list is refused.

### Backup & import

| Method | Path                           | Notes                                                                      |
| ------ | ------------------------------ | -------------------------------------------------------------------------- |
| POST   | `/v1/backup/config/export`     | JSON config backup; needs password (+ TOTP)                                |
| POST   | `/v1/backup/config/import`     | Restore a config backup; each table in it replaces the live one            |
| GET    | `/v1/backup/database`          | Live database file info                                                    |
| POST   | `/v1/backup/database/download` | SQLite snapshot; needs password (+ TOTP)                                   |
| POST   | `/v1/backup/database/restore`  | Replace the database with an uploaded SQLite file (multipart field `file`) |
| POST   | `/v1/import/:source`           | Import a `9router` or `omniroute` JSON backup                              |

Both restores write a safety copy of the current database first. A restored database must pass an integrity check and carry a schema no newer than the server's; an older schema is migrated up. Imports are additive: rows that already exist are kept and the backup's copy is skipped, so re-running an import is safe.
